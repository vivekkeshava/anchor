# Chaos campaign results

Generated by `python -m chaos.harness --runs 100 --kills 60 --seed <N>`.

## Method

A worker is spawned as a subprocess and `SIGKILL`ed at a uniformly random offset between
0.15s and 1.2s, repeatedly, until the kill budget is spent. Then undisturbed workers drain
the queue and the invariants are checked.

`SIGKILL` rather than `SIGTERM` on purpose: `SIGTERM` lets the worker release its lease and
finish its current step, which is the easy case. The interesting failure is the one where no
code of ours runs at all.

Simulated model latency is 50ms per call, so kills land *inside* runs rather than between
them. Without that, a campaign trivially satisfies every invariant while exercising no
recovery at all — which is why `runs interrupted+resumed` is reported alongside the rest.

## Reading the numbers

**Zero duplicates is the headline.** Counted in `side_effect_ledger` — the table standing in
for the downstream system — not in anchor's own `effects` table. Verifying a system's
correctness using its own bookkeeping proves nothing.

**"Needs review" is the guarantee being honest, not a failure.** 3 runs across 300 stopped
because a crash landed inside the effect barrier's window on a card charge, and anchor
refused to guess whether it had gone through. Retrying would risk charging twice. That is
~1% under a deliberately hostile kill rate — roughly one kill every half second against runs
that take a few hundred milliseconds. Under normal operation it is far rarer, and it never
reaches zero. This is why the claim is *effectively*-once.

**Replay is doing real work.** ~333 model calls against ~435 if every recovery restarted at
step zero: about 24% of model work avoided, with 108 runs recovered. The gap is the point of
the whole design.

**The journal never tore.** No run ended with holes in its step sequence or with a step
written under a stale fencing token, across 180 kills.

## A bug this campaign found

An earlier run of seed 23 **failed** with one duplicate `send_receipt`. The cause was in the
demo agent, not the runtime: `send_receipt` was declared `retry_safe=True` while its
downstream ignored the idempotency key it was handed. The barrier faithfully re-ran it after
a crash in the window, and the effect happened twice.

That is the one way to get duplicate effects out of this system, and it is worth stating
plainly: **`retry_safe=True` is a promise about the downstream that anchor cannot verify.**
The fix was to make the demo's downstream honour the key, as a real idempotent API does.
`tests/test_worker.py::test_retry_safe_tool_with_an_idempotent_downstream_effects_once` now
pins the behaviour.

Running a single seed would not have found this. Vary the seed.
